### 3. 🔴→✅ Bug de infraestrutura descoberto e resolvido: deploys falhando desde antes desta sessão
- O projeto tem um **Build Command customizado no painel do Vercel** (não está no `package.json`): `npx prisma generate && npx prisma db push && next build` — sincroniza o schema do banco automaticamente a cada deploy. Isso **não estava documentado em nenhum handoff anterior** — é bom o próximo Claude saber disso antes de mexer no `schema.prisma`.
- Eu (Claude) rodei `prisma db push` **localmente contra o banco de produção (Neon)** para criar a tabela `User` antes de commitar o código correspondente. Isso deixou o banco à frente do código.
- Quando o Marcelo clicou "Redeploy" no painel (tentando aplicar a env var), o Vercel rebuildou o commit **antigo** (`36c62e1`, sem `model User`), e o `prisma db push` tentou **apagar a tabela `User`** (que já tinha 2 linhas) — o Prisma corretamente recusou com a trava de perda de dados, e o deploy falhou (2x). **Produção nunca ficou fora do ar** — continuou servindo o último deploy bem-sucedido anterior.
- Resolvido ao fazer push do commit de login (que já tinha o `model User` batendo com o estado real do banco) — o deploy seguinte (`427849f`) passou limpo.
- **Lição para o futuro**: nunca rodar `prisma db push` local apontando pro banco de produção sem also commitar/deployar o schema correspondente logo em seguida — esse projeto sincroniza schema automaticamente a cada deploy, então banco e código-em-produção precisam ficar sempre em sync.
